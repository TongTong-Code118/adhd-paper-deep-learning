# 参考 05｜视觉优先设计合同（Visual Output Contract）

> 每一次论文导航与章节入口都必须优先交付 **真正可见的视觉结构**。本文件的作用是避免模型“写着要画图，最后只给出一个纯文本框”。

## A｜最重要的区分：“图形”不等于“表示图形的代码”

### 合格
- 在用户界面实际呈现的 SVG、图片、原生图示组件、可预览 Mermaid 图；
- 如果图形渲染确实不可用，以**分组卡片、表格、独立小节、带语义的缩进层级**展示，并明确说明渲染限制；
- 在可生成文件的执行环境，创建视觉文件，然后在回答正文里嵌入/链接**渲染结果**；代码藏在开发文件中。

### 不合格
- 像截图那样，上方出现 `纯文本` 标题，下面一整块文字和 `↓`；
- 写“流程图：第二章→3.1→七个因子→第四章”，却没有任何可见图；
- Mermaid/Graphviz/SVG 源码以代码块显示，却声称“图已画好”；
- 同一张信息卡完全复制为三张重复图，制造视觉噪音；
- 在缺失原文证据时擅自填入因子名称、回测收益或公式数据。

**图形验收问句**：“闭上眼不看正文，只看这张可见的图，是否知道每个节点承担什么工作、它们是什么关系？”如果不能，返工。

## B｜运行前的能力探测矩阵（不是要求调用不可用工具）

| 当前可用能力 | 第一选择 | 禁止事项 |
|---|---|---|
| 宿主支持原生图、图形组件、SVG 等 | 绘制真实的节点+连线+说明 | 用几行 `↓` 代替 |
| 文件/绘图工具可创建图片 | 生成 `.svg`/`.png` 并作为**图片呈现** | 仅贴文件的 XML 源码 |
| 平台已确认自动渲染 Mermaid（如 GitHub README） | 使用已确认支持的 Mermaid 预览 | 假设任何聊天窗口都支持 |
| 只支持普通 Markdown | 用小表格、语义标题、分组模块和间隔 | 输出一整个 `text` 围栏 |
| 连卡片/表格都不能渲染 | 分段标题+短列表，并坦诚能力限制 | 声称“已生成图” |

**注意**：Skill 是内容与执行规范，不是自动为任何聊天产品安装绘图引擎。不可控制的渲染器必须坦诚说明。

## C｜视觉层级：先认方向，再认细节

### C1 宏观地图：回答“我走到哪里了？”
- 适配论文真正的结构，优先 4–7 个核心节点；
- 推荐版面：横向流程（桌面）/纵向卡片（窄屏）；
- 节点用**原文小节名称+一句职责**，不是孤零零标题；
- 当前节点以**一个清晰的强调样式**高亮，其余节点淡化但仍可读；
- 箭头文字必须是有意义的谓词：“提供检验方法”“形成待组合因子”“检验假设”等；
- 如果原文只有截图片段，标示 `[来自截图片段，仅示意]`，不要误当已核实的论文整体结构。

### C2 章节逻辑：回答“这节具体怎么推进？”
- 本节标题保持原文；拆解来源/筛选/方法/推理/数据/检验等内容；
- 根据**真实关系**选图型：
  - 顺序型：横向阶段图；
  - 多分支：树状/分叉图；
  - 因果型：因果有向图，仅在原文证据支持因果时；
  - 依赖型：概念先备图；
  - 对比型：并排对照；不强行画箭头；
  - 推导型：变量到中间量到结果的分层链；
- 需要“这一小节为什么出现在这里”的文字 1–2 句。

### C3 概念机制：回答“它为什么会这样？”
- 类比图左边是现实，右边是专业结构，中间有明确对应；
- 单独画出关键变量变化而非画花哨背景；
- 边界/反例至少以一个醒目的标注列出；
- 不把类比关系描绘成实际证据。

### C4 公式结构：回答“数学符号在做什么？”
- 原式展示在图附近；展示输入、输出与中间操作；
- 同一符号在全文使用同一视觉标签/单位；
- 对复杂表达式优先展示外部结构，按需展开括号内公式；
- 数字例子必须能一步一步核算，最终带单位/百分比/百分点区别。

### C5 图表三棱镜：回答“看什么，有何结论，有何局限？”
- `看哪里`：圈出原图的一处轴、行、列、误差线、时间窗或参数；
- `说明什么`：用**可由原文核查**的数字或趋势说明；
- `不能说明什么`：给出不能外推的具体边界；
- 未获得原图时**不能伪造圈选**，只能解释原文图注或列出待核验位置。

## D｜视觉设计规范

### 布局
- 一个主图对应一个问题；不要在第一轮把所有章节的所有流程图倾倒出来。
- 总览：节点数建议 4–7；细节放子图或后续轮次（这是**设计启发值**）。
- 先“结构”，再“局部机制”，最后“数值与边界”，不一屏混合过多层次。
- 每个图用 1 个主标题、1 行短副标题、少量节点标签、必要的关系箭头。
- 图文相邻：图下方立即用一句话解释它为什么重要。
- 内容比较多时拆成上/下两张图；缩放不能把文字压到难以辨认。
- 窄屏：优先改竖排卡片，允许上下滚动，避免巨大水平滚动图。

### 字体、色彩、对比
- 使用清楚可读的中文无衬线字体（宿主默认字体即可）。
- 深色字+浅背景；至少保证足够对比；不要用淡灰字承载核心文字。
- 最多 1 种主要高亮色、1 种次级结构色、1 种警示色。
- 同一颜色必须在同一学习环节表达同样语义。
- 不能**只靠颜色**区分：同时使用文字标签、编号、实线/虚线。
- 视觉图表必须有文字替代说明或图像 alt，照顾无法辨色/读图的使用者。
- 避免复杂装饰、无关动画、闪烁；尊重 `prefers-reduced-motion`（若宿主支持）。

### 箭头和文本
- 每条箭头必须表达**顺序、依赖、验证、比较、因果或映射**中的明确一种。
- 默认文本 1–2 行。若标题过长，拆为“短标签+副说明”而不是塞满大方框。
- **语义优先于形状**：两个章节并列比较时不能画成“前一个导致后一个”。

## E｜严谨性与视觉的关系

1. **不能为了漂亮而补齐原文未知内容**。截图有 `3.2–3.8 七类因子`，但没有七个名字，就画一个聚合节点而不是脑补七种因子。
2. **对编号矛盾只标注待核**。若截图片段写“第二章”，但节号却是“3.1”，应清楚显示这个不一致，不能偷偷把第二章改成第三章。
3. **推论必须有来源身份**。原文证明/报告什么，与为了学习更清楚而新增的“通用方法学解释”，使用不同标签。
4. **图和正文不能互相矛盾**。有图时必须保留必要的文字边界说明。
5. 对主观学习体验不做不可靠断言：好的视觉是辅助理解，不是 ADHD 所有人保证记忆的捷径。

## F｜可重复检查的视觉场景

- 一轮初读 -> `宏观 SVG/组件` 出现；不是代码围栏。
- 进入 3.1 -> `小节图` 出现；呈现“当时可用信息、筛选、分组、调仓”。
- 进入公式 -> 变量关系及逐行数字演算；正确区分原文与假设。
- 看到截图中的 `第二章 + 3.x` -> 标注章号与小节号需核对。
- 无图形工具且 Mermaid 不确定 -> 不输出 Mermaid 源码；改用语义化卡片表格并明确限制。
- 用户说不要图 -> 允许偏离默认流程图强制要求。
- 用户是初学者 -> 高亮当前章节，解释箭头含义，而不展示全部技术细节。

## H｜v5.0：通过 MCP 真正绘图，而非展示源码

1. **先从原文核实结构**：读取真实章节名、概念和图表；保留不能核实的事项。
2. **按任务调用已注册的 MCP 工具**：`render_paper_map` / `render_section_flow` / `render_concept_diagram` / `render_formula_structure` / `render_evidence_prism`。
3. 每次提供 `source_note`：简短说明原文位置、数字是否教学模拟和任何不确定性；不能把漂亮图形当作新的原始证据。
4. **只在成功收到 ImageContent 且宿主真正显示图像时**，称“这张图显示”。MCP 未启用、工具调用失败或宿主不显示图片时，要说明原因，优先用实际支持的图形能力，不行就用结构化卡片回退。
5. 示例 PNG/SVG 只能用于展示预期样式。给**另一篇论文**画图要重新输入该论文实际内容，不得照搬示例节点与虚构数据。

工具服务器只支持有顺序的 2–7 节点流程图，以及概念/公式/三棱镜专用布局。多分支非线性因果网络需要更合适的可视化能力，不能强行画成一根线。
